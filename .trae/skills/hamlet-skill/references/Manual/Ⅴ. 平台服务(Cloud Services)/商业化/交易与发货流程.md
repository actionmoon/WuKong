# 交易与发货流程

抖音虚拟世界的交易流程由客户端发起，而核心的发货确认与状态同步则严格限定在 **Dedicated Server (DS)** 服务端进行。这种分离设计旨在防止客户端被篡改导致的发货异常，并利用服务端的稳定性确保数据持久化成功。

本篇为 Manual，讲解交易的整体架构、职责边界、幂等与补单机制、订单状态流转等**概念**。完整的可执行实践代码请见 Best Practice：

- Lua 实现：[交易与发货流程-Lua](../../../Best%20Practice/商业化/交易与发货流程-Lua.md)
- C# 实现：[交易与发货流程-CSharp](../../../Best%20Practice/商业化/交易与发货流程-CSharp.md)

> **🚨 前置条件**：商业化发货逻辑**必须运行在 DS 服务端**。严禁在客户端直接处理订单发货与数据落库——客户端发货缺乏官方补单机制支持，且极易受弱网、应用闪退等影响导致数据保存失败。

## 一、整体架构：客户端发起，服务端发货

抖音虚拟世界采用 **“客户端发起购买，服务端确认发货”** 的架构，以确保交易的安全性与幂等性。核心链路：

1. **客户端发起购买**：客户端调用 `DouyinMarketingService.Purchase` 拉起支付面板，玩家确认并支付星光币，通过 `onPurchaseResult` 获取支付结果。
2. **平台扣款**：支付成功后平台完成星光币扣除。
3. **服务端接收回调**：平台向运行在 DS 的服务端脚本发送 `onOrderPayment` 事件（携带订单序列号与票据 `DouyinReceiptInfo`）。
4. **服务端执行发货**：服务端验证票据后，将商品写入该玩家的 DataStore（原生 `DouyinDataStore`，以 `playerOpenID` 拼接为 `Scope` 隔离）。
5. **服务端同步状态**：落库成功后调用 `ConfirmOrder(code=0)` 通知平台发货成功；失败则通知平台触发补单。

## 二、职责边界（客户端 vs DS 服务端）

| 环节 | 执行方 | 关键接口/事件 | 说明 |
| --- | --- | --- | --- |
| 获取商品信息 | 客户端 | `GetProductInfo` / `GetProductInfos` | 购买前**必须**先获取一次商品信息并缓存，否则购买会失败 |
| 发起购买 | 客户端 | `Purchase(productId, productNum, orderData)` | 拉起支付面板；`orderData` 为创作者自定义透传数据，购买成功后经 `DouyinReceiptInfo.orderData` 原样回传，可用于关联业务上下文 |
| 购买结果 | 客户端 | `onPurchaseResult` | 支付成功/超时/失败回调 |
| 扣款事件 | 平台 → DS 服务端 | `onOrderPayment` | 扣款成功后向 DS 抛出 |
| 发货落库 | DS 服务端 | 原生 `DouyinDataStore` 写入 | 严禁在客户端执行 |
| 发货确认 | DS 服务端 | `ConfirmOrder(sequenceId, receiptInfo, code)` | 通知平台发货状态 |
| 手动补单 | 客户端 | `BackOrder()` | 数据加载完成后主动拉取遗漏订单 |

> **说明**：DS 服务端处理发货的脚本需挂载到带有 `DouyinServerRoot` 组件的节点下才能正常运行。

## 三、订单状态流转

一笔交易的订单状态由 `DouyinOrderStatus` 表示（详见 [数据结构参考](数据结构参考.md)）：

- `Init(1)` 创建未付款 → `Paid(3)` 已支付待发货 → `Shipped(4)` 已发货
- 异常分支：`Timeout(2)` 支付超时、`Failed(5)` 发货失败已退款

客户端 `onPurchaseResult` 回调返回时，订单一般处于 `Paid`（已支付待发货）；只有 DS 服务端成功调用 `ConfirmOrder(code=0)` 后，订单才流转为 `Shipped`。

## 四、补单机制

为防止丢单，平台针对以下场景触发补单：

1. 服务端未成功调用 `ConfirmOrder`；
2. 发货操作超时（2 秒内未完成）；
3. 发货状态码返回 `code > 0`。

- **自动补单**：用户**下次登录并在线满 1 分钟**时，平台自动核查待补发订单，并向服务端再次抛出 `onOrderPayment` 事件。
- **手动补单**：客户端可在用户数据完全加载完成后，主动调用 `BackOrder()` 触发补单。

## 五、幂等性保障（极其重要）

由于 `onOrderPayment` 可能因补单被**多次触发**，服务端发货逻辑必须实现**幂等性**，防止玩家被重复发货：

- **发货幂等**：以 `DouyinReceiptInfo.purchaseOrder`（全网唯一交易订单号）为主键，处理发货前先查库判断该订单是否已发放，已发放则直接跳过。
- **状态幂等**：
  - 若某订单已发货成功（`code = 0`），后续对该订单的任何重复请求都必须直接返回 `code = 0`；
  - 若某订单已退款（`code < 0`），后续对该订单的任何重复请求都必须直接返回 `code < 0`。
