# 房间服务

`DouyinRoomService` 是一个全局静态类，提供获取**当前对局 / 场景的全局标识与入口来源信息**的能力：房间 ID、所属世界 ID、邀请者、以及玩家的进入渠道。

本文档说明其能力概念、核心 API、关键字段与能力边界。完整的可执行案例（进入时获取并缓存、`enterFrom` 渠道差异化、邀请溯源）见 Best Practice。

---

## 一、核心 API 概览

| API | 说明 | 是否异步 |
| --- | --- | --- |
| `GetCurrentRoomInfo(callback)` | 异步获取当前房间信息（`DouyinRoomInfo`），通过回调返回 | 是（回调式） |

> `DouyinRoomService` 目前**只有 `GetCurrentRoomInfo` 一个方法**，是**只读**能力——只能获取当前房间信息，没有创建 / 加入 / 切换房间、也没有房间事件监听接口。

**`DouyinRoomInfo` 字段说明**：

- `roomID` (string)：当前对局的房间 ID。
- `worldID` (string)：房间所属的世界（地图 / 大区）ID。
- `inviterOpenID` (string)：邀请当前玩家进入房间的邀请者 OpenID（通过邀请链接进入时才有值）。
- `enterFrom` (int)：标识玩家进入该房间的渠道来源，见下表。

### `enterFrom` 渠道来源对照表

| 枚举值 | 含义说明 |
| --- | --- |
| `-1` | 其他渠道（默认或未知入口） |
| `0` | 逛一逛（平台推荐 / 信息流浏览进入） |
| `1` | 侧边栏（应用快捷入口进入） |

---

## 二、典型使用场景

- **渠道差异化 / 埋点**：玩家加入时读取 `enterFrom`，对「逛一逛」「侧边栏」等入口做差异化奖励或数据埋点上报。
- **邀请溯源**：利用 `inviterOpenID` 记录“是谁把该玩家拉进房的”，用于邀请激励、社交亲密度或组队自动绑定。
- **房间 / 世界标识**：用 `roomID` / `worldID` 做日志上下文、分区逻辑或与其他服务关联。

---

## 三、硬约束与能力边界

- **异步 + 判空**：`GetCurrentRoomInfo` 是异步回调，结果不会立即返回；回调中的 `roomInfo` 可能为空，使用字段前必须判空。
- **只读、无事件**：该服务只能查询当前房间信息，不能创建 / 切换房间，也没有“房间信息变化”事件。信息应在合适时机（如玩家加入）主动获取。
- **`inviterOpenID` 可能为空**：仅通过邀请链接进入时才有值；非邀请进入时为空，邀请激励逻辑需判空。
- **不要高频轮询**：房间信息在对局内基本稳定，应在玩家加入 / 初始化时获取一次并缓存，**切勿**在 `Update` / `FixedUpdate` 中反复调用。
- **区分身份**：`inviterOpenID` 是邀请者的 OpenID，不要与当前玩家自身的 OpenID 混淆。

## 四、常见问题（FAQ）

| 问题现象 | 原因 | 解决 |
| --- | --- | --- |
| 读取字段时报错 / 空引用 | 未判空直接使用房间信息对象 | 回调里先判空再读字段 |
| 邀请激励误发 | 邀请者标识为空未判 | 使用邀请者字段前先判空 |
| 卡顿 / 请求风暴 | 在每帧回调中反复调用 | 玩家加入时取一次并缓存，其余逻辑读缓存 |
| 渠道判断漏分支 | 未处理未知的进入来源 | 用常量映射 + 默认分支兜底 |
| 找不到创建 / 切换房间 / 房间事件接口 | 该服务只读，仅能查询当前房间 | 不要编写创建 / 切换 / 监听逻辑 |
| 身份混淆 | 把邀请者标识当成当前玩家标识 | 区分邀请者与当前玩家两个身份 |
