# 数据存储 DouyinDataStore

`DouyinDataStore` 是抖音虚拟世界平台提供的**通用键值对云端存储**核心类，用于在服务端持久化保存游戏数据（如玩家金币、背包、进度等）。数据以键值格式存储，值可以是数字、字符串、布尔值，或仅包含这些类型的表（表需序列化为字符串后存入）。

本篇为 Manual，讲解平台原生能力、核心概念、能力边界与限制、以及使用中必须处理的问题。完整的可执行实践代码请见 Best Practice：

- Lua 实现：[数据存储DataStore-Lua](../../../Best%20Practice/数据库/数据存储DataStore-Lua.md)
- C# 实现：[数据存储DataStore-CSharp](../../../Best%20Practice/数据库/数据存储DataStore-CSharp.md)

> **🚨 注意（DedicatedServer 模式）**：DS 网络模式下，所有云端数据库读写操作**仅允许在服务端执行**。如果在客户端发起请求，将直接收到 `-11002` 错误码。客户端需通过 `DouyinRemoteEvent` 或 `DouyinRemoteFunction` 通知服务端处理。

## 1. 能力定位

`DouyinDataStore` 是底层原生存储实体，直接使用有一定的编码成本：每次读写都需要先获取 store 实例；读写自定义表结构时需业务侧自行做 JSON 序列化与反序列化；不同语言各有其调用范式，具体写法见下方 Best Practice。

平台**不提供**开箱即用的数据管理框架类。若业务需要缓存、串行化、重试、JSON 自动编解码等能力，应在原生 API 之上**自行封装数据访问层**——按数据归属维度组织的做法见 [用户维度数据存储方式](数据存储方式/用户维度数据存储方式.md) / [精灵维度数据存储方式](数据存储方式/精灵维度数据存储方式.md)，完整框架代码见 Best Practice；本 Manual 不将任何业务封装描述为平台自带能力。

## 2. 核心概念：Name、Scope、Key

一条数据由 `Name` + `Scope` + `dataKey` 三段唯一标识。

- **Name（游戏名称）**：标识不同的游戏或业务模块，通常使用统一英文名，如 `"sim_game"`。长度不超过 20 字符。
- **Scope（作用域）**：区分数据的作用范围。推荐以玩家/精灵 ID 拼接形成，如 `"player_" .. playerOpenID`、`"pet_" .. petOpenID`，用于隔离每个玩家/精灵的数据。长度不超过 50 字符。
- **dataKey（数据字段名）**：标识具体字段，如 `"coin"`、`"level"`、`"player_data"`。最大长度 128 字符。

> **Scope 默认值与 `all_scope`（跨范围访问）**：`GetDataStore(name, scope, all_scope)` 中 `scope` 省略时默认为 `"global"`；`all_scope` 默认为 `false`。
> - `all_scope = false`（默认）：数据存储中所有 key 都自动带上当前 `scope` 前缀，只能访问该 scope 下的数据。
> - `all_scope = true`：可跨范围访问该 name 下所有 scope 的数据，此时需在 key 中用 `scope:key` 格式显式指定范围。
> 平台由此支持**跨范围搜索与前缀搜索**（详见能力边界 §3.5）。

**键设计示例：**

- 账号级数据：`Name="sim_game"`，`Scope="player_" + playerOpenID`，`dataKey="coin"`
- 精灵级数据：`Name="sim_game"`，`Scope="pet_" + petOpenID`，`dataKey="exp"`

> ⚠️ **不要**把 `playerOpenID` / `petOpenID` 当作 `dataKey`。单个 DataStore 的 key 数量约有 1000 个上限，用户量突破 1000 后会导致新增 key 写入失败。正确做法是把 `playerOpenID` / `petOpenID` 放进 `Scope`，`dataKey` 使用固定名称。

## 3. 能力边界与限制

### 3.1 容量与长度

- **Name**：非空字符串，长度不超过 20。
- **Scope**：长度不超过 50。
- **dataKey**：最大长度 128 字符（超限返回 `-10012`）。
- **Value**：单个 value 序列化后约 **6000 字符**为实践建议上限，超限写入会失败（错误码 `-10013`；该错误码的平台原始提示为“值大小超出了 32767 字节的限制”）。写入前应校验数据大小。
- **单个 DataStore 的 key 数量**：约 **1000 个**上限。超过后新增 key 写入失败（错误码 `-10014` / `-11005`），已有 key 的更新不受影响。建议采用“一玩家一 Scope”的拆分方式分散存储。
- **总容量**：每个世界数据存储上限通常约 **100M**（错误码 `-11004`）。

### 3.2 QPS / 频控

云端数据库有读写频控限制，不建议高频实时写入。

- 单个世界每分钟数据存储 API（所有读、写接口累计）**默认上限 900 次**，**峰值上限 1800 次**，超出的调用会失效（错误码 `-11001`）。
- **峰值规则**：若当前一分钟内没有 API 调用，则下一分钟峰值可达 1800 次。
- **建议**：玩家进入时读取一次并缓存到内存，离线时或定期统一落库，避免频繁操作同一 DataStore。

### 3.3 DS（Dedicated Server）模式

- DS 模式下数据存储**只能在 DS 服务端脚本上执行**；客户端调用任何存储 API 会返回 `-11002`。
- 数据存储业务逻辑需放在服务端，客户端通过 `DouyinRemoteEvent` / `DouyinRemoteFunction` 通知服务端处理。

### 3.4 Metadata

- Metadata 是 DataStore 的附加信息，平台自动管理数据的创建时间、更新时间、版本号等（见 API Reference 的 `DouyinDataInfo`）。
- 除平台自动管理外，允许附加自定义 Metadata：单条 metadata 值长度上限约 **1000 字符**，meta 键与属性大小也有上限（相关错误码 `-10016` Meta 键超限 / `-10017` 元数据属性超出 4096 字节）。建议仅在必要时使用，主要关注 value 数据的存储限制。

### 3.5 跨范围搜索与前缀列举

- 配合 `all_scope = true`，DataStore 支持**跨范围搜索与前缀搜索**：以 `scope:key` 格式定位数据，可按前缀批量列举同一 name 下不同 scope 的键或值。
- 平台在原生接口层面还提供 `ListKeysData` / `ListValuesData`（按 key 前缀分页列举键/值）等接口用于前缀列举；具体签名以源码及后续补充的 API Reference 为准，本 Manual 不展开完整用法。
- 前缀列举同样受 QPS 频控与分页限制影响，仅建议在管理/运维类低频场景使用，不要在高频游戏逻辑里遍历全量数据。

## 5. 使用中必须处理的问题（约束）

以下是平台约束带来的、业务层必须自行处理的问题。此处说明能力边界与约束；完整实现见 Best Practice。

- **新号场景**：读取会返回“数据不存在”（`-10001`）。业务需检测并初始化默认数据后再保存。
- **网络异常与重试**：遇到 `-10050`（DataStore 暂时不可用）等网络波动时，业务层应结合指数退避（如 1s → 2s → 4s）发起有限次数重试，并提供降级方案。
- **数据一致性**：相同 key 的写入需串行执行以保证顺序，不同 key 可并行；可通过写入队列或调用顺序衔接实现串行。
- **数据序列化**：DataStore 存储字符串。表结构需业务自行序列化为 JSON 再写入、读取后反序列化（平台 API 不提供泛型自动序列化）。序列化后需关注是否超过 value 长度限制。
- **实例管理**：每次读写都需获取 store 对象，建议对相同 `Name + Scope` 缓存复用同一实例，避免重复创建。
- **ID 选择**：账号级数据用 `playerOpenID`（总金币、关卡解锁等），精灵级数据用 `petOpenID`（属性、经验等），合理设计 `Name` / `Scope` / `dataKey` 结构。
- **数值 key 的存储类型必须全程统一**：同一个 key 一旦用于 `Increment` 计数，就应从初始化开始固定为数值类型（用数值 `0` 而非字符串 `"0"` 初始化，`Increment` 的 `delta` 传数值），读取时也按数值类型读。**切勿**对同一 key 混用字符串与数值写入。否则可能出现“存储值类型与读取类型不匹配 → 被误判为数据不存在（新号）→ 按默认值覆盖”的问题，典型表现是**计数在服务重启后被清零，且无报错无异常**（进程存活期内因内存缓存命中不易发现）。若线上已写坏，可换一个新的 key 名（如加后缀）绕开旧记录，避免脏数据继续污染读回。
- **`Name` / `Scope` 长度务必留足余量并主动排查**：除满足硬上限（`Name` ≤ 20、`Scope` ≤ 50）外，实践中建议 `Name` 取更短的稳定别名（如 `energy_avatar_ds` 量级），`Scope` 前缀尽量精简（如用 `"p_" + openID` 而非冗长业务全称拼接）。注意**模拟器环境下 `openID` 可能较长**（如 `SimOpenId__-` 前缀形态），加业务前缀后容易逼近上限。一旦 `Name` / `Scope` 超限，获取 store 阶段就会失败，业务表现可能是“操作没生效但看不到明显报错”。排查建议：在获取 store 前打印 `Name` / `Scope` 及其长度，并对所有数据库调用用完整异常/错误信息（而非仅一句摘要）记录，避免 fire-and-forget 吞掉失败。

> 编写数据库存取逻辑时（安全读取、异步/回调包裹、增量类型、JSON 长度限制等），请同时遵守全局统一的 **[编码约束与开发规范](../../Ⅲ.%20逻辑与脚本%28Logic%26Scripting%29/编码约束与开发规范/数据库开发约束.md)**。
