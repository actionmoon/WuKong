# 性能优化约束

本文用于指导 `抖音虚拟世界SDK` 开发的游戏在移动端和多人场景中的常见性能优化。

---

## 一、脚本与逐帧逻辑

### 1. 减少 `Update`、`FixedUpdate` 和 `LateUpdate` 工作量

- 仅把必须逐帧执行的逻辑放入逐帧回调。
- 状态变化优先使用事件驱动，低频检查使用节流计时器。
- 将同类对象的周期性检查分散到不同帧，避免同一帧集中执行。
- 对不可见、休眠、远距离或玩法未激活的对象暂停更新。
- `FixedUpdate` 只处理物理相关逻辑，不把普通业务轮询放入物理帧。
- `LateUpdate` 只用于确实依赖前序更新结果的逻辑，例如相机跟随。

### 2. 缓存高频访问结果

Lua 与 C# / Unity 对象之间存在跨语言桥开销。在高频路径中：

- 缓存稳定的 `transform`、`gameObject`、组件和服务引用。
- 缓存不会变化的计算结果、配置值和查找结果。
- 避免每帧调用 `GetComponent`、`GetComponents`、层级遍历、名称查找或服务查询。
- 获取指定 DouyinScript 时，使用 `GetDouyinScript(name)` 或 `GetDouyinScripts(name)`，不要通过 `GetComponents` 获取全部脚本后再筛选。

缓存 Unity / SDK 对象时仍须遵守对象判空和生命周期约束。可能被销毁或替换的 `DouyinActor`、`DouyinPlayer`、`DouyinPet`、`DouyinObject` 不应长期缓存对象本身，应缓存 ID，并在使用时通过对应服务反查和判空。

### 3. 降低临时分配与 GC

- 避免在逐帧、高频碰撞或 UI 刷新路径中反复创建 table、数组、List、字符串和闭包。
- 可复用的容器应在使用前清空，而不是持续创建新容器。
- 避免在循环中进行频繁字符串拼接、格式化、JSON 编解码和日志输出。
- 不在高频路径中使用会产生大量临时集合的查询或转换写法。
- 调试日志应支持分级和关闭；发布版本不得保留逐帧日志。
- 对象池应设置容量上限和回收策略，避免“池化”演变为永久持有全部对象。

### 4. 控制算法复杂度

- 避免在每帧对大量对象执行全量两两比较。
- 高频查找优先使用以稳定 ID 为键的映射，而不是反复线性扫描。
- 大列表的排序、寻路、批量统计和配置解析应在必要时触发，并按需分帧。
- 对空间范围查询使用分区、距离过滤或引擎查询能力缩小候选集。
- 先进行廉价判断，再执行射线、组件获取、序列化等高成本操作。

## 二、对象与生命周期

### 1. 避免高频创建和销毁

- 禁止在 `Update` 或高频计时器中持续调用 `Instantiate`、`Destroy`、`NetSpawn` 或 `NetDespawn`。
- 网络对象不得用本地对象池替代网络生命周期。

### 2. 创建与销毁 API 必须配对

| 创建方式 | 对应销毁方式 |
|---|---|
| `DouyinObjectService.NetSpawn` | `DouyinObjectService.NetDespawn` |
| `DouyinActor.NetSpawn` | `DouyinActor.NetDestroy` 或平台规定的同族销毁流程 |
| `UnityEngine.GameObject.Instantiate`（仅非网络对象） | `UnityEngine.GameObject.Destroy` |

不得混用网络 API 与 Unity 原生 API。挂载 DouyinScript 的网络对象必须走网络创建和销毁流程，否则会破坏同步与生命周期回调。

### 3. 注册与释放必须成对

- 事件监听、计时器、回调、临时资源和动态对象应在对应生命周期结束时释放。
- `Start` 注册的资源通常在 `OnDestroy` 清理。
- `OnNetSpawn` 注册的资源在 `OnNetDespawn` 清理。
- `OnActorSpawned` 注册的资源在 `OnActorDespawned` 清理。
- 断线不一定触发离开或销毁回调，重连初始化必须去重，避免对象和监听器重复增长。

## 三、物理优化

### 1. 控制物理参与规模

- 静态场景物体不要添加不必要的 Rigidbody。
- 不需要物理反馈的装饰物关闭 Collider 或使用更简单的碰撞体。
- 优先使用 Box、Sphere、Capsule 等基础 Collider；仅在确有必要时使用复杂 Mesh Collider。
- 复合碰撞体应减少子 Collider 数量，并避免重叠产生重复接触。
- 使用 Layer Collision Matrix 或精确的 Pair-wise 过滤减少无意义碰撞。
- 远距离或休眠区域的动态物理对象应停用或降级。

### 2. 降低查询与回调成本

- 射线、范围查询和落地检测应限制频率、距离和 LayerMask。
- 不在每个对象上逐帧执行相同的全场景物理查询。
- 一次性结算使用 `Enter`，不要使用 `Stay` 持续重复结算。
- 同一玩法事件只保留一个 Collision 或 Trigger 入口，并按玩法实体去重。
- 在物理回调中先做 Layer、Tag、ID 或状态过滤，再执行组件查询和业务逻辑。
- 不在碰撞回调中执行网络请求、复杂序列化、大量生成或同步加载。

### 3. 正确更新刚体

- 刚体施力、速度和位姿控制按物理规范收敛到 `FixedUpdate`。
- 不同时使用 Transform 和 Rigidbody 驱动同一个动态物体。
- 不为了“更稳定”随意提高物理频率；提高频率会近似线性增加物理开销。
- 高速物体仅在穿透风险明确时启用更昂贵的连续碰撞检测。

## 四、网络与平台服务

### 1. 降低网络写入频率

- 禁止在 `Update` 或高频计时器中每帧调用 `SetValue`、RPC、`NetSpawn` 或 `NetDespawn`。
- 连续状态采用阈值、时间间隔、变化检测和量化后再同步。
- 多项可合并的数据应批量发送，但需遵守 RPC 参数类型和单次消息大小限制。
- 不发送接收端能够从已有状态确定性推导的数据。
- 只向需要的目标发送消息，避免无条件广播。

常见同步间隔可从 100～500 ms 起步，再依据玩法实时性和实测流量调整。位置等高实时数据应优先使用平台提供的同步机制，不自行用 RPC 做逐帧广播。

### 2. 正确选择同步方式

- 必须可靠保持的持续状态使用同步变量。
- 允许丢失的一次性表现通知可使用 RPC。
- 写同步变量前必须确认网络已就绪且当前端持有主权。
- 接收端应基于状态变化更新表现，不做无意义的全量刷新。
- 网络对象生成前确认确有跨端可见需求；纯本地特效不应创建为网络对象。

### 3. 控制服务调用

- DataStore、排行榜、图片和其他平台服务按业务事件调用，不进行逐帧或高频轮询。
- 可复用且允许短暂过期的数据设置合理缓存和刷新时机。
- 合并重复请求，并对进行中的同类请求去重。
- 失败重试必须有次数上限、退避和取消条件，不允许无限快速重试。
- 异步回调返回后重新检查对象、页面和玩家生命周期，避免对已销毁对象继续更新。

## 五、常见反模式

以下写法通常会导致明显性能问题：

- 每帧查找对象、组件、玩家或服务。
- 每帧刷新全部 UI、重建列表或进行 JSON 编解码。
- 在碰撞回调中创建大量对象、写存档或广播网络消息。
- 使用无限轮询等待对象出现或服务返回。
- 通过持续创建和销毁处理可重复出现的短生命周期对象。
- 未设置上限的缓存、对象池、日志、历史记录或重试队列。
- 为避免偶发穿透而对所有物体启用最高成本的碰撞检测。
- 只在编辑器中验证性能，忽略真机、弱网和多人峰值场景。
