# 多输入源与 UI 协作约束

## 1. 概念 (Concept)
在复杂的玩法模块（如车辆、飞行器、武器）中，输入源通常同时包含：官方摇杆、键盘 WASD 和自定义 UI 按钮。

## 2. 边界 (Boundary)
- **业务模组必须掌握输入主权**：车辆、飞行器、武器的移动或发射逻辑必须在本地的业务脚本中形成权威状态。自定义 UI 只是补充输入源，不能成为唯一实现（除非明确声明是纯 自定义 UI 遥控面板）。

### 2.1 移动端可达性

- 本项目面向手游。玩家主动执行的操作必须有可点击或可触摸的移动端入口。
- 键盘按键可以作为 PC 调试或兼容输入，但不能成为唯一操作通路；存在键盘按键时，必须同时提供对应的移动端入口。
- 需要靠近具体对象才能发起的操作，使用基础交互按钮；进入玩法后持续可用的主、副操作，使用右下角操作按钮。按钮类型的使用边界见[交互按钮分类与使用规范](../../Ⅱ.%20界面与交互(UI)/系统交互按钮/交互按钮分类与使用规范.md)。
- 移动端可达性不改变上述边界：自定义 UI 仍是补充输入源；若自定义 UI 是唯一实现，必须明确声明为纯自定义 UI 遥控面板。

## 3. 机制与规范 (Mechanism & Specification)
- **统一汇入状态 Helper**：UI 事件、WASD、摇杆和官方按钮必须修改相同的输入变量或调用统一的 Helper 函数（如 `resolveDriveInput`）。
- **输入清零闭环**：在 `onMoveInputCancel`、按钮抬起 (`PointerUp`)、离座或对象销毁 (`OnDestroy`) 时，状态持有者必须主动将输入状态复位归零，防止状态残留。

## 4. 黄金法则与避坑指南 (Golden Rules & Pitfalls)
- **🚫 避坑：多套逻辑直接修改位移**
  严禁 UI 事件和标准摇杆各走一套逻辑直接修改 `rb.velocity` 或 `transform.position`，这会导致输入状态互相覆盖和撕裂。必须先汇入统一状态，再由单一驱动源执行位移。
