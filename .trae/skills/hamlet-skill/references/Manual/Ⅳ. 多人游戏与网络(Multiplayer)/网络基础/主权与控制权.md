# 主权与控制权

在 Douyin World 的网络同步体系中，**所有权 (Ownership)** 和 **控制权 (Controllership)** 是分离的两个核心概念。

## 1. 概念解析
- **主权 (Ownership)**：决定谁能写入该网络对象的**同步变量**，以及谁会收到跨主权消息。
  - 同一个网络对象在同一时刻**只有且只有一个主权方**，一个玩家可以同时是多个网络对象的主权方。
  - **主权必须存在**，任何网络对象在任何时刻都有一个明确的主权方，不会为空。
  - 只有主权方才能修改该对象的**同步变量**，非主权方写入既不报错也不同步（静默丢弃）。
  - 主权发生变更时，房间内所有人会触发事件广播。
- **控制权 (Controllership)**：决定谁被**逻辑上标记为该对象的操作者**，主要用于业务侧标注"当前是谁在使用这个对象"。
  - **控制权默认无归属**（不属于任何玩家），需要业务侧主动请求认领。
  - 控制权可以为空，也可以显式释放。
  - 控制权本身**不决定同步变量的写入鉴权**。
  - 只有控制权方才能直接控制对象的移动或特定交互动作。

> **注意**：所有主权 / 控制权判断都是网络行为，必须在网络就绪后调用。禁止缓存权限状态，每次使用前需重新查询。

## 2. 两类基础权限的核心差异

| 维度 | 主权 Ownership | 控制权 Controllership |
| --- | --- | --- |
| 业务语义 | 底层同步权威 | "当前谁在使用" 的业务标签 |
| 是否必须存在 | ✅ 必须存在，任何时刻都有明确的主权方 | ❌ 可以为空，默认无归属 |
| 是否可释放 | ❌ 不可释放 | ✅ 可主动释放 |
| 修改同步变量 | ✅ 只有主权方生效，非主权方静默失败 | ❌ 不影响 |
| 跨主权消息 | ✅ 消息路由到主权方执行 | ❌ 不影响 |
| 断线时的处理 | 框架自动迁移到其他玩家 | 离房时自动释放，断线保留在离线玩家上（需业务侧兜底） |
| 语言支持 | Lua ✅ / C# ✅ | Lua ✅ / **C# ❌（未开放）** |

## 3. API 接口 (Lua 与 C#)

### 3.1 主权判断与获取
- **Lua**：
  - 判断：`self:HasOwnership()` 
  - 获取：`self:GetOwner()` （可能瞬间为 nil，需判空）
  - 判断特定玩家：`self:IsOwner(player)`
- **C#**：
  - 判断：属性 `IsOwner`
  - 获取：属性 `OwnerPlayerId`（类型为 `ulong`，与 `DouyinPlayer.playerID` 的 `int` 对比时需注意转换） 或 `OwnerClientId`

### 3.2 主权转移请求与响应
- **Lua**：
  - 请求主权：`self:RequestOwnership(Action onFinished)`，回调的 `success` 返回 `true` 或 `false`。
  - 响应请求：在脚本中实现 `OnOwnershipRequest(senderID)` 函数返回 `true`/`false` 决定是否同意。参数 `senderID` 是**被请求的网络对象 UID**，不是发起者。
- **C#**：
  - 请求主权：`NetworkObject.RequestOwnership()`，同步返回 `OwnershipRequestStatus` 枚举（如 `RequestSent`, `AlreadyOwner`, `Failed`）。
  - 响应请求：订阅 `NetworkObject.OnOwnershipRequested += (clientRequesting) => { return true; }`，参数 `clientRequesting` 是**请求方的 clientId**。
  - 请求结果：订阅 `NetworkObject.OnOwnershipRequestResponse += (succeed, msg) => {}` 异步获取最终结果。

### 3.3 主权转移事件监听
- **Lua**：
  - `OnOwnershipTransferred(curOwner, preOwner)`，**全端广播**。不能将其视为“我拿到主权”的信号，必须在内部判 `self:HasOwnership()` 再做接管。
- **C#**：
  - 本端获得/丢失（推荐接管入口）：重写 `OnGainedOwnership()` / `OnLostOwnership()`。
  - 全局转移监听：重写 `OnOwnershipChanged(ulong pre, ulong cur)`。

### 3.4 控制权相关 (仅 Lua)
- **判断**：`self:HasControllership()`。
- **请求控制权**：`self:RequestControllership(Action onFinished)`。
- **事件监听**：`OnControllershipTransferred(prev, current)` 控制权转移时全端触发。
- **注意**：动态网络对象在创建后，其控制权并不默认归属创建者，通常需要在其同步变量就绪后延时主动请求控制权。

## 4. 主权变更的流程与方式

主权变更流程：**请求 → 审批 → 切换 → 广播 → 事件回调**。

1. **发起请求**：非主权方发起请求（前置检查是否已是主权；异步等待结果）。
2. **主权方审批**：当前主权方进行判断（返回 `true`/`false`），**禁止在审批回调内做副作用赋值**。
   - *Lua 审批规则*：返回 `true` 同意，`false` 拒绝；不实现审批方法等价于默认同意。若同一物体上有多个脚本实现了审批回调，**必须全部返回 true 才通过**。
   - *C# 审批规则*：`OnOwnershipRequested` 是 event。多订阅者的返回值合并按 C# event 语义处理（通常取最后一个订阅者的返回值），建议业务侧尽量只保留一个订阅者。
3. **广播回调**：主权归属切换完成后，通过服务器消息广播所有的客户端，触发响应的事件回调。

**主权变更的三条路径**：
- **请求式**：非主权方发起请求 → 主权方审批 → 切换 → 广播 → 事件回调。
- **指派式**（仅 Lua 支持 API，C# 需借助白名单绕行）：Lua 端主权方通过 `SetOwner(player)` 主动把主权指定给别人，跳过审批。
- **控制权联动**（仅 Lua 支持）：Lua 端请求控制权成功时，**主权也会一起自动转移到请求方**。

## 5. 主权方专属消息 (RPC / OwnerCall)

非主权方若需要触发主权方的独占逻辑，需使用专属消息机制。但请注意：**这些消息底层基于 UDP，不保证送达**。

| 场景需求 | Lua 侧实现 | C# 侧实现 | 核心原则 |
| --- | --- | --- | --- |
| **单向通知副作用** | `SendMessageToOwner("Foo", 1)` | `[Rpc(SendTo.Owner)]` 标记的方法 | 仅用于一次性特效、表现等不保证送达的通知。 |
| **需要双向回调结果** | `OwnerCall("Bar", onFinish, 2)` | `[Rpc(SendTo.Owner)]` 请求 + 主权方写 `NetworkVariable` 结果 | 关键业务数据必须用**同步变量**（`---@varSync` / `NetworkVariable`），**不要依赖 OwnerCall 的返回值**。 |

## 6. 转移机制与断线重连

主权和控制权在玩家**断线重连**和**应用切后台**时，表现出不同的转移逻辑：

| 触发场景 | 主权 (Ownership) 表现 | 控制权 (Controllership) 表现 |
| --- | --- | --- |
| **应用切后台** | **立即主动释放主权**，自动转移至房间内其他在线玩家。 | **保留**，不发生转移。 |
| **网络异常断线** | 服务器监测到断线后，主权转移至其他在线玩家。 | **保留**，不发生转移。 |
| **重连 / 切回前台** | 若玩家仍拥有控制权，会自动重新获得主权。否则需重新申请。 | 持续保留。 |
| **彻底退出房间** | **彻底放弃所有主权**（转移给其他玩家或 DS 服务器）。 | 玩家离房时，其获取的所有控制权会被**自动释放**。 |

### Case 分析：玩家 A (主控方) 切后台 / 断线
- 假设网络对象 D 的主权和控制权都在 A 身上。
- A 断线或切后台时，A 不会收到通知。B 和 C 会收到 D 的主权转移消息（主权可能转移给了 B 或 C）。
- A 重连或切回前台成功后，因为 A 仍保留 D 的控制权，系统会自动将 D 的主权交还给 A。此时 A、B、C 都会再次收到 D 主权转移回 A 的消息。
- **开发警示**：权威逻辑的接管（如开启定时器）必须是**幂等**的，要防御切后台带来的主权瞬间跳变。

## 7. 基础交互的主权与控制权逻辑

在业务开发中，常见的主权触发场景已经被 SDK 接口接管，业务侧**不需要**在这些场景手工写主权链路：
| 场景 | 框架接管行为 | 业务侧禁忌 |
| --- | --- | --- |
| 拾取 / 放下物品 | 拾取时**自动获取控制权**（因此顺带获得主权）/ 放下时**自动释放控制权** | 严禁在 `Pickup` 逻辑中手工添加 `RequestOwnership` 形成竞争 |
| 坐下 / 站起 | 坐下时**自动获取控制权** / 站起时**自动释放控制权** | 不要为座位组件补主权链路 |

### 7.1 载具座椅与载具根对象的权限边界

载具通常包含两个不同的网络对象权限问题：

- `SitDown` / `StandUp` 由具体座椅 NetworkObject 的座位框架处理；
- 载具根对象的 Rigidbody、速度、旋转和载具级同步状态由驾驶业务处理；
- SharedMode 驾驶应在 `OnSeatEntered` 确认落座后，对载具根对象调用 `RequestControllership()`；
- `RequestControllership()` 成功后通常同时获得控制权和主权，不能用 `RequestOwnership()` 代替物理控制权；
- 物理更新必须同时通过 `HasOwnership()` 与 `HasControllership()`；
- `OnSeatExited` 必须清零输入并调用 `ReleaseControllership()`，为下一名驾驶员释放控制权；
- 不要在驾驶座按钮点击阶段等待载具根对象的主权回调，否则主权申请失败或延迟可能阻塞本应由座位框架处理的 `SitDown`。

## 8. Pet 合养模式下的控制权与主权联动

Pet 模式（合养模式）下存在"精灵控制权"这条 SDK 内部机制，会额外影响业务侧网络对象的控制权归属。
- **注意**：Avatar 模式下没有此机制；另外 C# 侧目前无控制权 API，此联动只在 Lua 侧生效。

**典型场景**：
- 假设房间内两位玩家 A、B 互为合养关系，存在网络对象 D。
- 玩家 A 是精灵的主控方，B 是观察者；A 目前持有 D 的控制权（因此 A 也是 D 的主权方）。
- **当 A、B 切换精灵控制权时**：B 转为操控者，A 转为观察者。
- 此时**网络对象 D 的控制权会自动转移到 B**，B 也随之自动成为 D 的新主权方。

## 9. 运行模式差异：Dedicated Server 与 SharedMode

在 DedicatedServer（DS）模式下，主权的初始归属和运行规则与 SharedMode 存在明显差异。

| 对象类型 | Dedicated Server (DS) 模式主权归属 | SharedMode 模式主权归属 |
| --- | --- | --- |
| 静态网络对象（场景中预先摆放） | **自动归 DS 服务器所有** | 归属房主（Host）所有 |
| 玩家端创建的动态网络对象 | 主权归创建方玩家 | 主权归创建方玩家 |
| DS 服务器端创建的动态网络对象 | **主权归 DS 服务器** | （不存在此概念，由房主创建并持有） |

### 特殊规则
1. **静态对象修改**：DS 模式下的静态对象天然是服务器权威，客户端脚本里的“是否主权方”查询总是返回 `false`。
2. **断线迁移机制**：断线迁移规则**不适用**于服务器永久持有的主权。DS 服务器不会离房，因此属于服务器的主权不需要也不发生迁移。

## 10. 核心机制与开发规范 (黄金法则)

1. **网络就绪总闸**：在生命周期（`Awake`/`Start`/`Update` 等）中查询主权前，必须先验证网络是否就绪（Lua: `isNetworkSettled`，C#: `IsSpawned` 或 `isNetworkSettled`）。
2. **初始状态不可信**：`Awake` / `Start` 生命周期早于网络对象注册完成，此时主权状态返回值不稳定。初始化主权逻辑必须放在 `OnNetSpawned` / `OnNetworkSpawn` 中。
3. **写入必鉴权**：每一次对同步变量的写入前，都必须判断 `HasOwnership()` / `IsOwner`。非主权方写入会被静默丢弃。
4. **禁止缓存权限**：不要使用本地变量记录"我是否是主权方"，主权可能因他人请求、断线、切后台随时发生转移，每次操作前必须实时查询。
5. **审批只做判断**：在 `OnOwnershipRequest` 或 `OnOwnershipRequested` 回调中，只能进行逻辑判断和返回布尔值，**禁止编写任何赋值或表现层副作用**。副作用应放到转移完成的回调中处理。
6. **按钮路径权限闭环**（Lua 交互扩展）：普通 `interaction-button` 修改网络物体状态时，遵循 `isNetworkSettled` → `HasOwnership` → `RequestOwnership`。但载具物理驾驶是例外：必须先由具体座椅完成 `SitDown`，再对载具根对象执行 `isNetworkSettled` → `HasOwnership` → `HasControllership` → `RequestControllership`；不能用 `RequestOwnership` 代替 `RequestControllership`，请求失败时不执行物理写入。
7. **控制权释放闭环**：载具驾驶员在 `OnSeatExited` 中清零输入并调用 `ReleaseControllership()`；仅清空业务 Actor ID 或停止输入监听，不会释放网络对象的控制权。

## 11. 常见避坑指南 (FAQ)

- **Q: 为什么我写了同步变量，其他端却看不见变化，也没有报错？**
  A: 因为你不是主权方。SDK 规定非主权方写入同步变量会被静默丢弃，写入前必须包裹主权鉴权。
- **Q: 在 Lua 中，`OnOwnershipTransferred` 触发了，能直接执行权威逻辑吗？**
  A: 不能。该回调是**全端广播**，并非"我拿到了主权"的专属信号。必须在回调内 `if self:HasOwnership() then Start() else Stop() end`。（注：C# 中推荐直接使用 `OnGainedOwnership` 和 `OnLostOwnership`）。
- **Q: 玩家离开房间后又进来了，为什么主权没有自动还给他？**
  A: 离开房间等同于**永久彻底放弃**。只有断线和切后台属于临时失去，重连时若控制权仍在则自动归还。离房后的重新加入被视为全新玩家。
- **Q: 为什么在 `OnNetSpawned` 里面直接 `RequestControllership` 经常失败？**
  A: `OnNetSpawned` 触发时，网络对象刚注册完成，控制权链路可能尚未完全就绪。建议在同步变量的 `OnValueChange` 里发起请求，或延时 100ms。
- **Q: Lua 中的 `OnOwnershipRequest(senderId)` 和 C# 中的 `OnOwnershipRequested(clientRequesting)` 参数有什么区别？**
  A: 区别极大。Lua 的 `senderId` 是被请求的**网络对象 UID**，无法借此区分是哪个玩家发起的请求；而 C# 的 `clientRequesting` 是**请求方的 clientId**，可以用来做白名单审批。
