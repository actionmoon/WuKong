# 网络模型概述

在抖音虚拟世界（Douyin World）中，根据玩法的联机需求、防作弊要求以及逻辑复杂度的不同，平台提供了三种核心的网络运行模型：**Single Player (单机模式)**、**Shared Mode (共享模式)** 和 **Dedicated Server (DS 模式)**。

在开发初期选择正确的网络模型，能大幅降低后续重构的成本。本文档将对这三种模式进行总览对比，帮助你做出合理的架构选型。

---

## 一、三种网络模型核心对比

| 维度 | Single Player (单机模式) | Shared Mode (共享模式) | Dedicated Server (DS 模式) |
| --- | --- | --- | --- |
| **联机方式** | 单机，纯本地运行 | 多人联机，分布式计算 | 多人联机，权威服务器计算 |
| **服务器进程** | 无 | 无独立服务器（房间服务器仅做消息中继） | **有**官方托管的独立服务器进程 |
| **业务执行位置** | 客户端独立执行 | 每个客户端各跑一份，通过同步保持一致 | 关键逻辑集中在 DS 服务器，客户端只做表现 |
| **权威判定** | 无 | 由持该对象“主权”的客户端执行 | 由 DS 服务器统一执行 |
| **反作弊能力** | 无 | **弱**（客户端可篡改本地代码/内存，无中心校验） | **强**（服务器逻辑和代码对客户端不可见） |
| **场景需求** | 普通 Unity 场景 | 仅包含 `DouyinWorldRoot` | 额外需要 `DouyinServerRoot` 节点 |
| **网络对象生成** | Unity 原生 `Instantiate` | `NetSpawn` (任一客户端调用，调用方持主权) | `NetSpawn` (DS端调用) + `ServerSpawn` (仅DS可见) |
| **通信通道** | 无 | 客户端之间 `SendMessageToXxx` | 客户端 ⇄ DS服务器 走 `RemoteEvent` / `RemoteFunction` |
| **数据存储 (DataStore)**| 客户端直接读写 | 客户端直接读写（建议主权方操作以防并发覆盖） | **必须在 DS 脚本调用**，客户端调用将报错 `-11002` |

## 二、模型选型指南 (黄金法则)

在决定项目架构前，请严格按照以下标准进行选型判定。**请注意，从 Shared Mode 升级到 DS 模式并非一键切换，通常需要重构 30%-50% 的核心代码。**

### 1. 什么时候选 Single Player？
* 纯单机解谜游戏、单人剧情体验。
* 个人空间、私密装扮房间。
* 不需要多人看到彼此，但需要连接云端记录个人积分、调用排行榜或保存个人存档（可使用 DataStore/Rank）。

### 2. 什么时候选 Shared Mode (默认)？
* 休闲社交、虚拟装扮、剧情互动。
* 低难度小游戏（跑酷竞速、休闲解谜、简单合作等）。
* **不涉及**公平竞争的多人协作玩法。
* **无虚拟资产、无付费内容**的纯体验型玩法。
* 玩法初期原型的快速验证（验证通过后再考虑是否升级 DS）。

### 3. 什么时候必须选 Dedicated Server (DS)？
只要你的玩法涉及以下**任意一条**，就必须选择 DS 模式：
* ⚔️ **强竞技玩法**：需要严格的防作弊和公平性保障（如射击对战、MOBA）。
* 🎲 **随机与概率**：抽奖、扭蛋等，随机结果必须由不可篡改的服务端生成。
* 🏆 **排行榜奖励**：积分来源需经服务端严格校验以防止刷榜。
* 💰 **商业化核心**：涉及虚拟资产交易、道具付费购买等。
* 🛡️ **核心资产保护**：任何“玩家获益行为”均需服务端授权。
* 💾 **高安全数据存储**：由于 Shared Mode 下客户端可以直接篡改代码来刷 DataStore 数据，对数据安全有要求时必须走 DS。
