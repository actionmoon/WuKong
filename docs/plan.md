## 2. 已确认的参考实现

### 2.1 加载与运行

入口 `index.html` 引用 `src/style.css` 和 ES module `src/main.js`。Import Map 指向站内 Three.js、Three.js addons、WebGPU/TSL 与 `three-mesh-bvh`。当前主程序使用 Three.js Renderer 与 BVH；存在 Import Map 配置不代表 WebGPU 已启用。

`assets.js` 定义 27 项核心资源，通过 HTTP 并发下载，等待 Meshopt Decoder 就绪后解析 GLB、JSON 和碰撞数据。它也支持从用户选择的本机资源目录读取文件；当前在线站点提供了资源请求响应。

运行状态为 `loading → ready → fight → victory / defeat → fight`。`requestAnimationFrame` 驱动循环，单次步长上限为 `1/20` 秒。每帧依次处理玩家、Boss、危险物、特效、双方命中、角色分离、相机、HUD 与音频。完美闪避可减速 Boss 与危险物，玩家保持独立时间尺度。

玩家与 Boss 在出生点重置。玩家进入 `forceFightBox` 可强制 Boss 进入战斗。胜利与失败分别延迟约 2.5 秒、2.2 秒展示结束界面；Enter 或点击重新挑战。

### 2.3 资源引用与数据

核心契约按来源保留相对路径：

1. 场景：`assets/arena/arena.json`、`arena.glb`、`collision.bin`。
2. 虎先锋：`assets/tiger/tiger.glb`、`tiger.anims.json`、`stone_decoy.glb`。
3. 天命人：`assets/player/wukong.glb`、`wukong.anims.json`。
4. 法术、棍势、变身动作：`assets/player/` 下的 `spells`、`stances`、`bianhua` GLB 与动画 JSON。
5. 广智变身：`assets/transform/gycy_lang.glb`、对应动画 JSON。
6. 广谋与毒蛇：`assets/spirit/gycy_she`、`gycy_shebang` GLB 与对应动画 JSON。
7. 数值：`assets/data/player.json`、`tiger.json`、`spells.json`、`stances.json`、`bianhua.json`。
8. 表现：`assets/vfx/vfx.json`、`assets/audio/audio.json`，以及配置和脚本继续引用的贴图、声音包、音乐文件。

`player.json` 包含属性、移动、体力、闪避、五段轻棍、疾跑轻棍、重棍、棍势、葫芦和受击配置。`tiger.json` 包含 51 项技能定义、5 条阶段配置、AI 行为树与连招配置、伤害公式、霸体 / 硬直、Buff 和 4 项投射物定义。配置数量不等同于全部功能已运行验证。

`vfx.json` 包含 26 项纹理定义、75 项系统定义；`audio.json` 包含 293 项事件定义、动作 / 命中映射、脚步和 BGM 配置。`sfx.bin` 是声音片段打包文件，不能直接作为一个 AudioClip 使用，需按配置偏移与字节数拆出片段并检查格式。

`collision.bin` 支持原始三角网格及 `WKC1` Meshopt 压缩格式；本次实测为 WKC1，包含 457,494 个顶点、846,228 个三角形，文件长 4,341,227 字节，与头部声明一致。Unity 移植需先解码，再按区域拆分、评估简化并建立静态碰撞网格。

本次下载的 10 个 GLB 均通过文件头和声明长度校验，实际声明 `KHR_meshopt_compression`、`KHR_mesh_quantization`；带贴图的模型还声明 `EXT_texture_webp`，场景额外声明 `EXT_mesh_gpu_instancing`。导入工具必须兼容实际的 KHR Meshopt 扩展，不能仅凭支持旧的 EXT 扩展就判断可用。场景包含 570 个 mesh 和 940 项嵌入图片；角色及动作包合计包含 304 个动画剪辑。目标工程当前没有声明 glTF / Meshopt 导入依赖，不能把下载的 GLB 直接视为已可被 Unity 导入。

`character.js` 以精确剪辑名绑定动画，合并动作包时按节点名匹配骨骼。动作时间由脚本显式驱动，包含分段跳转、播放速率窗和独立根运动采样；向目标移动的缩放率按攻击距离与双方半径计算并限幅。移植应避免 Animator 根运动与 Lua 位移重复应用。

`combat.js` 用攻击骨骼 / 挂点在前后帧之间扫掠的球体，对目标竖直胶囊做距离检测；按动作播放实例、SweepCheck 分组和目标去重。`damage.js` 按配置计算攻击倍率、减伤、防御、真实伤害、暴击与随机浮动，最终向下取整；DS 结算应保持相同公式并提供可固定随机输入的诊断入口。

虎先锋源码明确 `maxPoise = 0`，其硬直由动作霸体窗处理，没有独立可耗尽的架势条；不因 HTML 存在 `boss-poise` 元素就新增该机制。

核心初始数值：玩家 HP `390`、MP `220`、体力 `250`、葫芦 `6` 次；Boss HP `6480`。后续逐项沿用配置中的单位，例如暴击率按万分制，不能将源 `500` 误读为 500%。

资源提取时发现法术纹理文件名由 `vfx.addTextures()` 统一拼接到 `assets/vfx/`，与 `spells.json` 所在的 `assets/data/` 无关；变身模块另动态注册 4 张新增纹理。清单保留误定位请求的 404 及正确路径映射，这些已解决，不代表资源缺失。

参考文件与校验：

- [下载清单](reference/wukong/inventory.json)：来源、字节数、SHA-256、错误路径的解析修正。
- [资产分析](reference/wukong/asset-analysis.json)：161 个文件，88,946,212 字节（约 84.8 MiB），字节数与 SHA-256 校验全部通过，未解决的游戏资源下载失败为 0。站点根目录 `favicon.ico` 返回 404，单独记录，不参与游戏资产验收。
- [在线浏览器证据](reference/browser-evidence.json)、[在线加载截图](reference/wukong-loading.png)。
- [本地参考运行证据](reference/local-reference-evidence.json)、[本地参考战斗截图](reference/wukong-local-fight.png)：运行提取的原网页，属于参考基线，不是 Unity 克隆运行结果。

### 2.4 坐标和操作基线

源场景单位为米，Y 向上，采用右手坐标系。Unity 导入后需统一手性转换，联动验证位置、旋转、骨骼、三角绕序、法线、根运动和命中盒；不重复套用源数据已经完成的 UE 厘米转换。

| 配置 | 源值 |
| --- | --- |
| 玩家出生点 | `(0, -1.237, 0)`，源 yaw `-1.59626` |
| Boss 出生点 | `(-1.226, -6.343, 48.157)`，源 yaw `1.68932` |
| 战斗区圆心 / 半径 | `(0.274, -6.419, 38.657)` / `16.26 m` |
| 强制战斗触发盒中心 | `(-1.039, -0.398, 33.654)` |

源 `Character` 朝向与场景 yaw 相差 `π/2`，迁移时与手性转换一起验证。

键鼠操作基线：WASD 移动、Shift 疾跑、Ctrl / Alt 慢走、Space 闪避、左键轻棍、右键重棍 / 蓄力、V 棍花、Z / X / C 切棍势、1 定身、2 聚形散气、4 赤潮变身、F 广谋精魄、R 葫芦、Q / 中键锁定、M 静音、H 帮助。触屏界面提供摇杆与操作按钮，横屏进入战斗。

## 3. 移植方案

### 3.1 方案比较

| 方案 | 收益 | 代价 / 限制 | 结论 |
| --- | --- | --- | --- |
| Unity + Hamlet Lua，沿用 DedicatedServer | 符合现有配置，可验证跨端状态，复用源资源与配置 | 需拆分原单机逻辑并处理资源格式 | 推荐 |
| Unity + Hamlet SinglePlayer | 与原网页运行模型接近，迁移链路较短 | 改变项目网络偏好，不满足当前默认目标 | 不在本轮采用 |
| Unity 内嵌网页 | 能直接复用网页 | 不能完成原生 Hamlet 场景、对象和脚本克隆 | 不在本轮采用 |

### 3.2 架构与还原边界

- 客户端负责输入、角色表现、相机、UGUI、音效和特效。DS 负责 Boss AI、技能合法性、消耗、命中、伤害、状态效果和挑战结算。
- 可见的 Boss、危险物与持久战斗状态通过共享网络对象表现；服务端专属控制器放置在 `DouyinServerRoot`。创建与通信按 Hamlet 对应 API 文档实现。
- 保持原作单人挑战规则：按真实玩家建立独立挑战上下文；第二客户端用于验证旁观表现、状态传播及后加入，不默认增加合作玩法。上下文和可见性机制在步骤 2 核实 SDK 支持后落定。
- Avatar 保持平台一对一玩家关联。天命人模型、动画和变身的装配方式先用最小样例验证；在可行性得到证据前不承诺平台 Avatar 可任意替换。
- 将源动画事件、根运动、攻击窗、取消窗、无敌窗和技能配置转为 Lua 可读取的数据。原 Web 渲染或音频参数需按 Unity 单位和效果校准。
- 不增加商店、排行榜、付费、存档或额外关卡。当前挑战状态不需要云端存储，调试固定 `--data-store off`。

### 3.3 目标文件组织

拟新增文件放入 `unity/Assets/WuKong/`：

- `Scenes/WuKongTiger.unity`：克隆专用场景。
- `Art/`、`Animations/`、`Audio/`、`VFX/`：转换后资产。
- `Prefabs/`：Boss、技能表现、危险物和 HUD。
- `Lua/Shared/`：配置、动作契约和共享状态模块。
- `Lua/Client/`：输入、镜头、界面与表现逻辑。
- `Lua/Server/`：战斗控制、Boss AI、技能和结算模块。
- `Editor/`：确有需要的资源转换与场景装配辅助。

源网页参考资源保存在 `docs/reference/wukong/`，不直接加入 Unity 构建。资源映射、转换参数及验证结果随步骤记录。现有 `SampleScene` 和工程设置已存在用户修改，后续以新场景工作并按差异检查保留已有工作。

## 4. 分步执行与验收

每一步遵循：执行 → 核对预期 → 将实际结果与证据写入第 5 节 → 人工确认 → 下一步。步骤内修复和必要回归属于当前步骤。

### 步骤 1：参考采集、分析与计划

1. 用 `agent-browser` 打开原站，提取入口、模块和实际请求。
2. 下载脚本依赖、核心资源及配置引用资源，记录 URL、HTTP 结果、字节数和 SHA-256。
3. 阅读源码，建立模块、数值、坐标、输入和资源迁移清单。
4. 尝试加载及最小操作取证；区分源码证据与运行证据。
5. 生成本文，检查范围、证据和步骤验收条件。

预期：参考资源有可核验清单，计划覆盖完整玩法，运行采集结果如实记录。

### 步骤 2：Unity 连接、资源导入与 Hamlet 最小样例

1. 连接 `unity-mcp`，确认目标工程、活动场景与 Console；保存当前工作后创建克隆场景。
2. 核实支持实际 `KHR_meshopt_compression`、WebP 与 GPU 实例扩展的 GLB 导入链路，先转换 / 导入一个带贴图与动画的角色样例。必要时安装适配 Unity 2021 的工具，并验证 SDK 构建兼容性。
3. 检查骨骼、蒙皮、动画、WebP 纹理、坐标和材质；解码碰撞格式并用小范围样例验证。
4. 按 Hamlet 文档建立 Lua Loader、DS 脚本和共享对象，验证 Avatar 与天命人模型装配方式及挑战上下文。
5. 用 `unity-mcp` 调用 `Tools/ScenePackage`，确认构建产物更新；按 `hamlet-debugging` 先 dry-run，再启动 DS 与两个客户端。

预期：Unity MCP 可实际读写正确工程；最小模型正常显示并播放动画；客户端与 DS 进入克隆样例场景，共享状态变化可观察。此处决定后续资产管线，失败不继续批量转换。

### 步骤 3：卧虎寺场景与视听基线

1. 转换场景资产，复现材质、灯光、天空、血池与环境。
2. 导入解码后的静态碰撞，设置出生点、战斗区域和触发盒。
3. 建立平台相机、避障、锁定目标和 HUD 基础布局。
4. 构建并启动调试器，按出生点、寺庙通道、楼梯、战斗区移动路线验证。

预期：玩家和 Boss 出生位置及方向正确，路线可通行、不穿地；镜头不穿主要遮挡物；对照原站同角度截图检查场景构图。

### 步骤 4：玩家基础动作与战斗

1. 迁移输入汇聚、走跑、疾跑、转身、闪避、锁定和动作衔接。
2. 迁移五段轻棍、疾跑轻棍、重棍蓄力、棍势资源、受击和葫芦。
3. DS 校验并结算体力、伤害、治疗、无敌窗和同次攻击目标去重；客户端同步表现。
4. 使用固定输入用例验证打击时间、连招、取消、耗尽体力、完美闪避和重复攻击。

预期：动作与配置时间轴对应；一次命中不重复扣血；消耗、治疗和 HUD 数值一致；其他客户端观察到相同战斗结果。

### 步骤 5：虎先锋 AI 与完整挑战循环

1. 迁移感知、强制战斗触发、距离决策、阶段、连招和技能选择。
2. 迁移拳剑攻击、冲击与投射物、石化 / 石像分身及相关受击表现。
3. 将原技能定义与实际代码支持项逐项对照，记录行为树和技能时间轴映射。
4. 验证远近距离、各血量阶段、打断、双方死亡和挑战重置。

预期：Boss 技能前摇、攻击窗和结束条件符合参考；阶段变化、伤害与危险物一致；胜利 / 失败及重试完整重置状态和对象。

### 步骤 6：棍势、法术、变身与精魄

1. 迁移三种棍势、棍花、连招派生与相应资源规则。
2. 迁移定身法、聚形散气、破隐攻击、赤潮变身和广谋精魄。
3. 验证魔法 / 能量消耗、冷却、定身破除、隐身仇恨、变身退出与毒蛇投射物。
4. 覆盖缺资源、连续施法、施法中受击、技能中死亡与重试的状态清理。

预期：源配置支持的操作都有可运行对应项；模型 / 动画切换自然，资源和效果跨端一致，重试后无残留状态。

### 步骤 7：界面、音效、特效与性能

1. 完成血条缓动、体力 / 魔法 / 棍势、技能冷却、葫芦、锁定、帮助与结束界面。
2. 解析并拆分声音包，映射脚步、攻击、命中、技能和 BGM，验证静音与重新挑战。
3. 还原武器拖尾、命中特效、法术、石化、变身、毒蛇与相机反馈。
